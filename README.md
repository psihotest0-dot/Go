# Agent API & Memory Backend

***English** · [Български](README.bg.md)*

A high-performance Go monolith backing an AI Agent service, providing vector similarity search, long-term memory consolidation, and standard chat streaming. It runs on the host (Windows is the primary target, Linux/macOS work too); PostgreSQL, the embedder, Prometheus and Grafana run in Docker.

## Tech Stack
* **Language**: Go 1.26 (`go.mod` pins the toolchain, 1.26.11)
* **Database**: PostgreSQL 15 (requires `pgvector` and `pg_trgm` extensions; the bundled image is `pgvector/pgvector:0.8.7-pg15-bookworm`, PostgreSQL 15.19 with pgvector 0.8.7; an existing database is upgraded by recreating the container and running `ALTER EXTENSION vector UPDATE;` in each database that has the extension, after a full backup)
* **SQL Query Builder**: `sqlc` (with `pgvector-go` overriding PostgreSQL vector types)
* **Migrations**: `goose`
* **Job Queue / Background Tasks**: River (PostgreSQL-backed, replacing Redis)
* **LLM Integration**: Standard OpenAI Go SDK pointing to a custom "Lemonade" provider (OpenAI-compatible server; the tuned setup is Gemma 4 12B instruction-tuned, `Gemma-4-12B-it-GGUF`, with a 32k context split into two 16k slots; Qwen 3.5 9B was used before and still works)
* **Embedding Model**: `intfloat/multilingual-e5-small` via FastAPI Python sidecar (CPU only)
* **Chat front ends**: the Flet desktop client (separate repository) and an optional Telegram bot
* **Observability**: Prometheus & Grafana (JSON logging via standard `slog`)

## Architecture & Features

### Orchestrator Pipeline
The main agent orchestrator (`internal/agent`) implements a streaming pipeline using Server-Sent Events (SSE). It handles:
1. Fetching history from PostgreSQL and fitting it into a token budget (`LLM_HISTORY_TOKENS`, `LLM_HISTORY_MESSAGES`); older turns are replaced by a rolling summary. The history window keeps its start from turn to turn and is cut back to 60% of its limits in one step when it is full (not slid by one message every turn), so a model server can reuse the cached start of the prompt.
2. Generating real-time embeddings for the user's prompt using the embedder sidecar.
3. Fetching semantically similar long-term memories and document chunks via Hybrid Search.
4. Calling the LLM with the context and streaming response chunks directly to the user. The model may call tools (search, web search/fetch, saving a memory, proposing a global rule); the output is cleaned of `<think>` blocks and tool markup before it is shown or stored.

All token budgets of one request derive from the context window of one slot (`LLM_CONTEXT_TOKENS`, e.g. `16384` for a 32k server with two slots); every budget can also be set explicitly. See [Configuration](#configuration).

**Questions at the end of a reply.** How often Lili ends a reply with a question is decided by the code, not by the prompt: a rule in a prompt loses to the history of the conversation (measured with the real model and the real history: 11% of the replies ended with a question without a history, 62% with it). Every 4th reply of a conversation is asked, by a short note placed next to the person's last message in the copy that goes to the model, to end with ONE question about a detail of what was said (not a generic one); the other replies are asked to end with a statement. The count is of all replies of the conversation, a regeneration asks for the same ending as the reply it replaces, a message with code or a conversation with an attached file gets no note, and the note is never stored (`internal/agent/closing_note.go`).

**One reply at a time in a conversation.** A conversation is a person and a session id; the app (`/chat/stream`, `/chat/regenerate`) and the Telegram bot can both write to it, and the Telegram session `tg-<chat id>` is meant to be open in both. A turn takes the conversation from the moment its question is stored until its answer is stored; a turn that finds it taken waits (first come, first served), so the second one reads the first answer in its history and the stored order is question, answer, question, answer. The wait counts in the time of the request (5 minutes for the app, 3 for Telegram); when that ends first nothing of the turn is stored and the app gets `503` (Telegram says the conversation is busy). Conversations of different people or sessions never wait for each other. A client that sends `"queue_events": true` is told with `event: queued` that it waits (see `docs/openapi.yaml`); the old clients are not sent the frame. The lock is in memory, so it holds for one backend process; it is not taken by background work (the summary, memory analysis) or by tools. The app finds the Telegram conversations of a person with `GET /telegram/sessions` (`tg-<chat id>` for each chat tied with `/link`; `api.TelegramSessionID` is the one place that builds the id) and reads a long conversation backwards with `GET /messages?session_id=…&before=<id of the oldest message it shows>` (messages stored in one instant are told apart by their ids). **What is written in the app shows in Telegram too.** When a question is answered in the app (`/chat/stream`, `/chat/regenerate`) in a conversation shared with a Telegram chat (`tg-<chat id>`), the bot repeats it in that chat: "📱 Ти (в приложението):" with the question (cut at 500 characters), then the answer as any other answer of the bot (for a new answer to the last question, a line "🔄 Нов отговор…" instead of the question). The repeat is made before the conversation is let go, so the answer to a Telegram message that waited behind it comes after it; it has 10 seconds, and whatever happens there never changes the answer or its storage. It goes only to a chat that is on `TELEGRAM_ALLOWED_CHAT_IDS` AND linked to the same user (the session id comes from a request, so `tg-<any number>` is not a way to write to a stranger's chat); a conversation of the app that is not a `tg-` one, a failed answer and a reply of the model that only "thought" are not repeated. Metric: `telegram_mirror_total{result}` (`sent`, `not_allowed`, `not_linked`, `failed`). The Telegram bot's own answers are not repeated back to it.

Metrics: `chat_session_waits_total{result}` and `chat_session_wait_seconds`.

### What the model saves, and what waits for the user
* **Memories** (`create_memory`) are saved at once: what to remember is the model's decision, as in a conversation between people. A memory written in a turn that read a web page or a document carries `metadata.source = "chat_tool"` and `metadata.external_sources`, so a doubtful one can be found and deleted later (`GET /memories`, `DELETE /memories/{id}`).
* **Global rules** (`save_global_rule`) do not write directly, because a rule is the first thing in the system prompt of every session. The model's request becomes a **proposal** that waits for the user (`GET /proposals`, `POST /proposals/{id}/approve|reject`, or `/pending`, `/approve`, `/reject` in Telegram). A proposal that rests on text from the web or from a document says so. Global rules (they apply to every session) are capped in number and can be listed and deleted (`GET /rules`, `DELETE /rules/{id}`). The chat stream announces new proposals with an `event: proposals` frame. **Notes on how to talk** (`save_style_note`, up to 8) take the same path: the model proposes an observation of how the user likes to be talked to (humour, length, depth), the user confirms it, and the prompt shows the notes in a section of their own ("Как говорим ние двамата"); `GET /rules` lists them with `kind: "style"`. Measured on 2026-11-14 with five hand-written notes on 18 real messages: closing phrases 15 → 10, the cliché "винаги съм готова" 4 → 0, emoji on jokes 0 → 4.
* **Deleting a chat** (`DELETE /chat/sessions/{id}`) removes the messages, the rolling summary, the traces and the attached files of that session in one transaction. Memories are kept (they only lose the link to the message). A user message the background memory job has not read yet is moved to a `deleted:<id>` session and removed after it has been read, so a fact told just before the chat was deleted still becomes a memory.

### Files attached to a conversation
A text file (code, a log, a long paste) can be attached to **one conversation** (`POST /chat/attachments`, see `docs/openapi.yaml`). It is not the library: nothing is split, embedded or summarised, and other conversations never see it. The prompt shows the newest files in full (every line with its number) within about 4 000 tokens, which are taken from the history and the retrieved context; the model looks into the rest, or into any file, with the `read_attachment` tool (a part by line numbers, or the lines that contain a text, so a function can be found in a file of thousands of lines). Limits: 256 KB a file, 20 files and 1 MB a conversation; a file nobody attaches again for 30 days is removed. The text of a file is untrusted: a memory written after reading it carries `external_sources: ["attachments"]`, and a global rule waits for the user as always.

### Memory Consolidation
Background memory consolidation runs asynchronously via River queues (`internal/jobs`).
The pipeline implements:
1. **Fact Extraction**: Calls the LLM specifying a JSON schema to extract structured facts (`fact_key`, `value`, `statement`, `is_explicit_change`) from unanalyzed messages.
2. **State Management**: Facts change atomically within a single SQL transaction: a memory is `candidate` or `active`. If a new fact contradicts an older one explicitly, the older one is deleted and the new one becomes `active` (said again later, the old fact is stored anew). Until 2026-11-14 a replaced fact stayed as `superseded`, out of every search; migration 00029 deleted those rows and removed the status.
3. **Concurrency**: Implements PostgreSQL advisory locks using explicit `conn` handles and `crc32(UUID)` keys to prevent concurrent workers processing the same user's memory tree.
   *Warning: Session-level advisory locks do not work properly when used with PgBouncer in transaction pooling mode.*
4. **Distillation** (`ENABLE_DISTILLATION`, on by default): after a book is ingested, the LLM writes concept summaries of it in the background. This is slow (it can take days for a large library) and shares the model with the chat through the background share of the slots (`LLM_BACKGROUND_SLOTS`).

### Vector Search
Retrieval operates via **Hybrid Search**, combining:
* `pgvector` cosine similarity (`<=>`, HNSW indexes)
* a lexical side: PostgreSQL full-text search with prefix matching (`to_tsvector('simple', …)` with a GIN index) over document chunks, which stands in for Bulgarian stemming; `pg_trgm` `word_similarity` over memories

Results are merged directly inside optimized SQL CTEs using Reciprocal Rank Fusion (RRF) with `k=60` and returned to the caller.

Two details matter for a library with books in more than one language:
* **Associative search.** The `search_documents` tool first finds the concept summaries nearest to the question and lends their themes to the text side, so a Bulgarian question also finds passages of an English book (on 11 questions with a known answer, a chunk of the right book was among the first five results 11 times, against 6 before). **English query.** `search_documents` also takes an optional `query_en`, the same query in English, which the model is told to give whenever the query is not in English; both are searched and the passages are merged by score (a passage found by both once, at most 8). Measured on 2026-11-08 with 97 files and the real model (Gemma 4 12B): on 6 questions about English books, asked twice, the model found a passage of the right book in 12 of 12 turns against 6 of 12 without it (a Bulgarian question about Peter Pan, an English book, now finds it); on 10 questions about Bulgarian books it made no difference (18 of 20 both ways). A sentence in the system prompt that only recommended an English search was tried first and dropped: the model then searched in English alone and missed Bulgarian books (14 of 20 against 18).
* **Candidate pool and result count.** The vector scan keeps the 400 nearest chunks (not 200) before filtering, and `search_documents` returns up to 8 passages (`search_memories` 5). On 33 questions with a known answer this put a chunk of the right book among the results 27 times instead of 25, and a relevant passage 22 times instead of 19, at the same search time (about 10 ms) and about 1 000 more tokens per call. **Index recall.** The HNSW index is approximate, and on the short keyword queries the model sends it can miss the nearest chunks of the whole library: on 2026-11-11 the three nearest chunks of a Bulgarian keyword query about Marcus Aurelius were in the right book, but the 400 candidates the index returned held none of them, so the book was never found. `hnsw.ef_search` is therefore 1000, the most pgvector allows (it was 400). On 98 queries with a known right book (47 full questions and 51 queries the model really sent) the right book was among the first eight results 78 times instead of 77, and that query went from missing to third, while a search stays at 15-16 ms. An exact scan finds it 83 times, but takes 1.3 s. **One index per script.** The remaining misses were not a matter of density (m=32, ef_construction=200 gave 78 again): in one graph the chunks of the English books formed an island a Bulgarian query did not reach — for "Питър Пан къде живее" the 32 nearest chunks of the whole library were all from the English book, and none was among the index's 400 candidates. Since migration 00028 the raw chunks have two partial indexes, Cyrillic and the rest, and the search takes 400 candidates from each: on the same 98 queries (2026-11-14, a copy of the live library) the right book is among the first eight 84 times instead of 77, more than the exact scan of a single pool, at 17-21 ms instead of 16.
* **Search inside one file.** A question that names a file of the library ("what does CLBSV2.pdf say") is about that file: `search_documents` then searches only inside it (`SearchFileChunks`: no per-file cap, no distance limit, an exact scan through the `file_id` index) and tells the model so (`searched_only_in_file`). A file is named by its whole name with the extension, or by its title together with a word such as "file", "document" or "book" (or a title that holds a digit); a title that is part of another file's name needs the whole name, and two equally good matches mean no choice. Before, a question about one file got two of its passages and six of other books, which the sources panel listed too: 32% of the results came from the named file on 33 test questions, now 100% (12-107 ms), with no false alarm on 28 ordinary questions and 46 real messages. A query of fewer than seven letters without a question word is filler and is skipped; it is not skipped when the question names a file (the model sent "CLBSV2" and got nothing: 3 empty answers of 3 on the real model, 3 correct summaries of 3 now). A follow-up that no longer names the file ("and what else is in it?") is not covered.
* **Language-aware distance limit.** A question is farther from passages in another language than from passages in its own, so a chunk whose language differs from the question's gets 0.03 more distance before it is dropped (`chunkCrossLanguageMargin`).

No distance limit can tell an answer from an off-topic hit with this embedding model (nearest relevant chunks at 0.10-0.21, nearest chunks of questions the library cannot answer at 0.18-0.21), so the model that reads the results is the one that judges relevance.

**Where it knows from.** Asked "where do you know it from", the model said that its memory is a library it keeps reading (8 of 15 answers on three wordings of the question); a last reply rule with a sample sentence tells it to say plainly that it answered from the language model's own knowledge, learned in training, when it made no lookup in the turn, and to offer to check the books (0 of 15 claimed a library, 14 of 15 offered the check). One line among the tool lines changed nothing (7 of 15).

**Facts of the world.** The system prompt tells the model not to answer from memory a fact that the library did not answer (people, places, events, records, numbers, dates, names, prices, news), but to call `web_search`, read the best page with `web_fetch` when the snippets do not answer, and name the source; arithmetic, the meaning of everyday words and conversation need no search. Measured on 2026-11-11 with the real model (Gemma 4 12B), the real tools and the live library: the highest peak of Rila was answered correctly in 2 of 2 tries with the rule against 0 of 2 without it (the model named a wrong peak), the winner of a world cup was once given the wrong opponent without it; on 6 questions about books asked 3 times each, the right book was found by `search_documents` every time and the web was not used (0 of 18, with or without the rule), and 2 trivial questions and one conversational message never went to the web either. The price is about one second and one more call to the search service for most factual questions (13 of 15 turns against 4 of 15). On well-known facts both answered correctly. `web_fetch` is rarely reached: the first round of a question that opens with a question word is forced to `search_documents` and a turn has two tool rounds, but in 280 measured turns the model never asked for a third.

### Embedding model and cache
Every vector in the database (chunks, memories, the cache) comes from the one model named by `config.DefaultEmbedModel`. The backend checks at start that the embedder runs exactly that model and refuses to store vectors from any other.

To avoid repeated computation, embeddings are cached in the `embedding_cache` table under a SHA-256 of the **model name and the text**, so a change of model never returns a vector of the old one. A batch of texts costs one cache read and one write. **Cache rule:** an entry is removed when it has not been used for **7 days** (`last_accessed_at`; a hit renews it, at most once a day). The `embedding_cache_gc` job runs daily and deletes in batches of 1000 until nothing old is left. Hits and misses are counted by kind of text (`cache_hits_total{kind="query"|"passage"}`: a search question or anything else). Measured on 2026-11-08 with the whole library of 97 files in: the table is 350 MB (31 % of the database), about 95 % of its entries repeat a vector that `document_chunks` already stores (80 % pieces of books, 15 % summaries), only 60 of 164 000 entries were ever used again after their first day, and the hit rate over three days was 0.2 %; so the cache pays off only for a repeated run of the same ingest (a retry), and a full dump was ~270 MB larger because of it. That is why the rule is 7 days, not 30, and why the entries that repeat a stored vector were deleted on 2026-11-08 (164 507 → 6 288 entries, 350 MB → 13 MB); a re-ingest of a book later than a week after the last one embeds its pieces again.

**Changing the embedding model** is a deliberate operation, not a setting: vectors of two models are not comparable.
1. Change `DefaultEmbedModel` (and `VectorDimension` plus the `vector(...)` columns in a migration if the dimension changes) and the model loaded by `services/embedder`; rebuild the embedder image.
2. Stop the backend and run `go run ./cmd/reembed -force`. It recomputes the vectors of **memories and document chunks** (`-memories=false` / `-chunks=false` limit it). It does not need the original files.
3. Back up first (`scripts\backup.ps1`); a full re-embed of a large library takes hours of CPU. The old cache entries are no longer read and disappear with the 7-day rule.

If the extraction itself changed (a better PDF parser, say), use `go run ./cmd/reingest` instead: it queues the ingest of the stored originals again. It can only do that for files whose original is still in `storage/` (see `KEEP_ORIGINALS`); the others are left alone, with their text and vectors untouched.

## File Ingestion Pipeline
The system supports uploading external knowledge documents via the `POST /v1/files` endpoint (also served as `POST /files`).
1. **Upload & Verification**: Enforces a 100 MB limit (`MAX_UPLOAD_MB` changes it; larger files get `413 file too large`), hashes the file for deduplication (a duplicate is answered with `409` and the existing record), securely saves it to the local `storage/` directory, and writes a tracking record. The original stays there after the ingest unless `KEEP_ORIGINALS=false`. The upload itself accepts any file type; the format is judged by the ingest job.
2. **Extraction**: The `internal/ingest` module picks the parser by the **MIME type sniffed from the file's first 3072 bytes (`mimetype`) or by the file extension** — either one is enough. Supported: plain text (`.txt`, `.md`, `.csv`, `.json`, `.yaml`, `.yml`, `.log`), HTML, PDF, DOCX, XLSX, EPUB and images. PDF text comes from Poppler's `pdftotext`; pages with almost no text are treated as scans and OCR'd (`pdftoppm` + Tesseract with the `bul` and `eng` languages). Images go through Tesseract directly. The encoding of HTML and of EPUB chapters comes from a BOM, a `<meta charset>` or the XML declaration; a Project Gutenberg book keeps only the text between its `*** START OF …` and `*** END OF …` lines, without the title page and the licence. A file that cannot be read (unsupported, empty, password protected, no text) ends in status `failed` and is not retried.
3. **Background Chunking**: An async River job (`IngestFileWorker`) extracts the raw text, splits it into chunks, generates vector embeddings, and stores them in the `document_chunks` table for retrieval.
4. **Embedding Status**: `GET /v1/files` (also available as `GET /files`) reports `chunk_count`, `has_embeddings` and `embedding_status` per file. Embeddings live in PostgreSQL via `pgvector` — there is no external vector store. `embedding_status` mirrors the ingest status but maps a `completed` file with zero chunks to `empty`, so the UI can distinguish "indexed" from "ingested but nothing to search".

## Telegram bot
The bot starts when `TELEGRAM_BOT_TOKEN` is set. **It answers nobody until `TELEGRAM_ALLOWED_CHAT_IDS` lists the chat ids it may talk to** (comma separated); the token only controls the bot, not who may write to it.
1. Write `/id` to the bot — it answers with your chat id (the only command open to everyone).
2. Put the id in `.env` as `TELEGRAM_ALLOWED_CHAT_IDS=<id>` and restart the backend.
3. Commands: `/link <user-uuid>` ties the chat to an existing backend user (by default the chat gets a user of its own); `/pending` lists the proposals waiting for confirmation, `/approve <n>` and `/reject <n>` decide them. Any other text is a chat message. The bot works in private chats and understands text only (files go through the web client). The messages of one chat are answered one at a time, in the order they arrived. A chat that is not on the list gets nothing but `/id`, answered once per chat every 10 seconds (at most 8 such replies at a time); its other text is dropped at once and logged once a minute per chat.

**How the replies look.** The model writes Markdown, so the bot sends its answers as Telegram HTML: `**bold**`, `*italic*`, `~~strike~~`, `` `code` ``, fenced code blocks, `http`/`https` links, bullets and headings (a heading becomes bold); a table stays text, and a mark with no partner (`2 * 3 * 4`, `snake_case`) stays as it was written. Text of the model that looks like HTML is escaped, so it cannot become markup, and a link of another scheme (`javascript:`, `tg:`) is not a link. A long answer is cut at a blank line, else a line end, else a space, into pieces of at most 4000 characters; a code block that a cut falls into is closed and opened again, so each piece is a whole message. If Telegram answers "can't parse entities" the piece is sent again as plain text, as the model wrote it; any other failure is logged and not repeated. What the bot says itself (errors, `/pending`, the notice of a proposal) is plain text. Code: `internal/telegram/format.go` (`markdownToHTML`, `splitReply`), `sendAnswer` in `bot.go`.

## The Oracle (second opinion for the trading bot)
The trading bot ([`alpaca-roundtable-trader`](https://github.com/psihotest0-dot/alpaca-roundtable-trader), a separate project, paper trading only) asks this backend for a second opinion on each signal of its strategy. It sends the signal with the numbers around it (indicators, the last bars, volume, the account and its limits) and up to five cleaned news headlines; the model answers `APPROVE`, `VETO` or `HOLD` with one short sentence of reason in Bulgarian. The bot's risk engine still decides every order. The model never proposes an order, a size or a price.

* **Routes.** `POST /oracle/evaluate` and `GET /oracle/ping` need `Authorization: Bearer <ORACLE_TOKEN>` and no `X-User-ID`. They are served only when `ORACLE_TOKEN` is at least 32 characters; otherwise they do not exist. `GET /oracle/decisions` (the journal, below) is an ordinary route with `X-User-ID`. The contract is in [`docs/openapi.yaml`](docs/openapi.yaml).
* **What bounds a planted sentence.** The model has no tools, no memory, no history and no access to the database. The news is cleaned twice (the bot and here: one line, no addresses, markup or invisible characters, the length cut) and shown as quoted data. The reply is held to a schema whose verdict can only be one of the three words; anything else, a reply cut off at the token limit, or a model that does not answer is **not a verdict**: the call is asked once more, then fails with `502`/`504`, and the bot reads that as `HOLD`, never as a yes. Cleaning cannot recognise an instruction in plain words, so the design relies on this limit, not on the cleaning.
* **Repeats.** Asking again about the same `signal_id` returns the earlier verdict with `cached: true` (a `HOLD` for 3 minutes, a final verdict for 30), and two questions about one signal at once share one call to the model. The work goes on when the bot has stopped waiting, so that its next question finds the answer.
* **The journal.** Every call, answered or failed, is a row of `oracle_evaluations` (verdict, reason, model, tokens, time, the request as received, and two labels: `signal_version`, the strategy version the bot sent, where `oracle-probe` marks the bot's own test questions, and `prompt_version`, a 12-character hash of the question the model was asked — the system prompt, the answer schema, the call settings and the layout of the facts — which is also returned in the reply of `/oracle/evaluate`, so that a changed prompt starts a new period of the evaluation instead of being guessed from dates). The bot first runs in **shadow mode**: it ignores the verdicts, and the journal is the whole result, to be compared later with what the signals went on to do (the bot's backtest can replay an exported record of verdicts: `export-oracle-decisions`, `--replay-oracle`). Judge it only on signals that come after the day it was switched on, never on old news (the model has seen the past).
* **One verdict for both modes.** The bot asks the same signal in two modes (`shadow` for its evaluation, `active` from a container that follows the verdict). The verdict belongs to the `signal_id`: the call that comes second is answered from the first (`cached: true`), whichever mode it is. It still leaves a light row of its own mode in the journal (`served_from` = `cache` or `joined`; the verdict, reason, model and prompt label are those of the answer it repeats; attempts, tokens and latency are 0; migration 33), written in the background so that the answer does not wait for it. Only one such row exists for a signal and a mode (a unique index), and none when the mode already has a row of a call that reached the model, so the journal shows a signal in every mode that asked about it and the repeats of a HOLD do not fill it.
* **Metrics.** `oracle_requests_total{outcome,mode}` (`answered`, `cached`, `failed`, `unauthorized`, `bad_request`), `oracle_verdicts_total{verdict,mode}`, `oracle_latency_seconds{mode}`; `mode` is `shadow`, `active` or `none` (the body did not say, or the call was refused before it was read), and every series exists at zero from the start. A `cached` call counts in the mode of the caller, a verdict in the mode of the call that made the model give it. The alerts add the modes up. On the development machine a call takes about 1.5 to 2.5 seconds with `Gemma-4-12B-it-GGUF`. Three alerts in `prometheus/alerts.yml` (group `oracle`) watch them: `OracleGivesNoVerdict` (2 or more calls without a verdict in 30 minutes), `OracleCallsRefused` (a wrong token or an unusable body) and `OracleSlow` (an average over 8 seconds). Nothing is sent anywhere: an alert is something to look at in Prometheus or Grafana. The prompt is `internal/prompts/oracle_system.tmpl`.
* **Turning it on.** Make a token (`python -c "import secrets; print(secrets.token_hex(24))"`), put it in this backend's `.env` as `ORACLE_TOKEN` and in the bot's `.env`, and restart the backend; the start log says whether the route is on. The new table is created by the migration at the start.
* **The Oracle on DeepSeek.** `PAID_LLM_ENABLED=true` (with `DEEPSEEK_API_KEY`) makes the Oracle ask the paid DeepSeek API instead of the local model; `false` (the default) keeps everything local, whatever else is set. `ORACLE_LLM=local` keeps the Oracle local even when the paid model is on (for the day the chat uses it), and `ORACLE_LLM_MODEL` names the model (default `deepseek-flash`). The chat is not touched. The start log warns when it is on; an unknown `ORACLE_LLM`, or `true` without a key, stops the start (a typo must not quietly pick a model). There is no fallback to the local model when the paid one fails: the bot gets a failure, which it treats as a HOLD. The request is sent with thinking off, without the local-only fields and with `json_object` in place of the strict schema (the prompt names the JSON). The `model` column of the journal changes to the paid model, the prompt label stays the same, so the bot's judge starts a new period by itself. **Limit and money.** `PAID_LLM_DAILY_USD` (default 1.00) is the most the paid model may cost in a local day, estimated at the peak prices (an upper bound); at it the Oracle answers HOLD until midnight and no request is sent. A restart does not give it a fresh start: the day's cost is read back from the journal. The balance of the account is read once an hour (`paid_llm_balance`); alerts: the limit reached, the balance under $0.50, requests failing (a 401 or 402 means the key or the balance). The tokens are counted too: `paid_llm_tokens_total{kind=cache_hit|cache_miss|output}`, `paid_llm_requests_total`, `paid_llm_spend_today_usd` - cost = (cache_hit x hit price + cache_miss x miss price + output x output price) / 1e6; prices of 2026-11-14 for `deepseek-flash` are $0.006 / $0.30 / $1.20 per million tokens at peak, half off peak (api-docs.deepseek.com/quick_start/pricing; the table is `prices` in `internal/llm/spend.go`). Measured: about $0.0005 per signal, i.e. $0.02 on a day of 40 signals. **The chat on the paid model.** With `PAID_LLM_ENABLED=true` two kinds of chat turns go to the cloud: a question to the library (a book, a passage, what the library holds) unless `LIBRARY_LLM=local`, and any turn of a conversation the owner sent there (`use_paid: true` in `/chat/stream` and `/chat/regenerate`, the "cloud" button of the client; `use_paid: false` keeps even a library question at home). The same prompt and tools are used. If the paid model fails before it has done anything (no limit left for the day, no network, a refusal of the provider) the same turn is asked of the local model; after a tool has run or a word was sent it is not repeated. The stream ends with an `event: model` frame that says who answered (only while the paid provider is configured). The limit of `PAID_LLM_DAILY_USD` is one for the Oracle and the chat together; what the day has cost is kept in the table `paid_llm_spend` (migration 32), and at the start the count goes on from the larger of that and an estimate from the Oracle's journal, so a restart forgets neither. Background work (memory, summaries, distillation) stays local. To put the library on the paid model while the Oracle stays on the local one (the bot's judge is on its first period), set `PAID_LLM_ENABLED=true` AND `ORACLE_LLM=local`. Measured on 2026-11-14: blind, 14 Bulgarian questions - 6 answers for the local model, 5 for the paid one, 3 equal; the paid one was about 2.5 times faster. The privacy policy of DeepSeek (2026-02-10): data is stored in mainland China, may be used to train models (opt-out by e-mail), no fixed retention; the owner has accepted it for the library and the cloud conversations.

The backend reads the environment, and a `.env` file in the working directory is loaded at start (see `.env.example`). Unset means the default; an unparsable number or flag in the `LLM_*`, `MAX_UPLOAD_MB`, `AUTO_MIGRATE` and `EMBEDDER_TIMEOUT_SECONDS` variables is logged as a warning and the default is used.

### The model server (Lemonade)

These settings live in Lemonade, not in this backend. They are what the chat was tuned and measured with on 2026-11-02: `Gemma-4-12B-it-GGUF` on a 16 GB GPU with 32 GB of RAM.

* **Context.** `ctx_size` 32768 with `--parallel 2` gives 16384 tokens per slot, which is what `LLM_CONTEXT_TOKENS` assumes. Lemonade's automatic size can come out smaller (31022 gave 15616 per slot). After loading, look for `n_ctx_slot` in Lemonade's log (`%TEMP%\lemonade-server.log`).
* **Options per model** go through `POST /v1/models/<id>/options`, for example `{"ctx_size": 32768, "llamacpp_args": "--no-mmproj-offload --cache-ram 0 --ctx-checkpoints 2"}`. The model's own sampler defaults from Lemonade stay in force that way; a `llamacpp_args` sent with the load request replaces them.
* `--no-mmproj-offload` keeps the vision projector off the GPU (the chat sends no images).
* `--cache-ram 0 --ctx-checkpoints 2` stop llama.cpp from keeping prompt snapshots in RAM. Without them the server grew from 7.8 to 15-17 GB of RAM during a short test; with them it stays at 8.5 GB and the speed is the same (about 62 tokens/s, a reply in about 1.7 s).
* **One model at a time.** The 12B takes 11.9 GB of the GPU and the 9B 9.7 GB, so they do not fit together. Set `LLM_MODEL`: when it is empty the backend takes the first model by name from `/v1/models`, and a newly downloaded model can change that.

Scripts and tests: `TEST_DATABASE_URL` (integration tests; the database name must contain `test`), `BACKUP_DIR`, `BACKUP_KEEP` (backups), `GRAFANA_ADMIN_PASSWORD` (required by `docker compose`).

## Observability
- Centralized JSON logging using standard `slog` with enforced `request_id` and `user_id` context tracing via HTTP middlewares.
- Before returning any HTTP 500 Internal Server Error, explicitly log the error using `slog.Error` so it is not lost.
- Prometheus metrics are exposed at `/metrics`: `api_requests_total` and `api_request_duration_seconds` (labelled by route pattern, not by raw path), `stage_duration_seconds` (pipeline stages), `llm_tokens_total`, `llm_queue_wait_seconds` (waiting for a model slot), `llm_silent_streams_total` (answers cut off after 8 s of silence: `retried`, `kept_partial`, `failed`), `cache_hits_total` / `cache_misses_total`, `retrieval_nearest_distance` and `retrieval_results` (the quality of a search, after the distance limits: the cosine distance of the nearest result the vector half found, and how many results came back, 0 included; `search="chunks"` is the `search_documents` tool, `search="context"` the concept summaries of the prompt), `ingest_jobs_total` / `ingest_job_duration_seconds`, `distillation_summaries_total`, `memory_facts_dropped_total{reason}` (facts of the memory analysis not stored because their evidence is not the person's words: `no_evidence`, `not_in_message`, `name_not_a_name`), `agent_proposals_total`, `agent_web_tool_requests_total` (paid), `agent_tool_calls_total{tool,result}` (every call of a chat tool: `ok`, `refused` — the model got the call wrong, `failed` — the server failed, `bad_args`, `duplicate` — the same tool with the same arguments again in one turn, not run; a name the model made up is `tool="unknown"`), `chat_session_waits_total{result}` / `chat_session_wait_seconds` (chat turns that had to wait for their conversation: `served`, `gave_up`), plus gauges for the job queue and for files by ingest status.
- Visualize them with the pre-configured Grafana dashboard (`grafana/dashboards/main.json`). Alert rules are in `prometheus/alerts.yml` (Prometheus and Grafana show them, and Alertmanager sends `critical` and `warning` ones to the owner's Telegram chat through the bot of the chat, `info` ones never; configuration in `alertmanager/`. The token and chat id come from `alertmanager/secrets/`, which git ignores: create the two files once with `scripts\alertmanager-secrets.ps1`, which reads `.env`, then `docker compose up -d alertmanager`. Check the file with `amtool check-config`, see the comment in `alertmanager/alertmanager.yml`). Their unit tests run with `promtool`; the command is at the top of `prometheus/alerts_test.yml`.
- The same Prometheus also scrapes the trading bot (another project, with its own compose): the job `alpaca-trader` in `prometheus/prometheus.yml` reads `host.docker.internal:9101` (trader) and `:9102` (observer), which the bot publishes on the host loopback. Its series all start with `alpaca_`. Its alert rules are the group `alpaca-trader` in `prometheus/alerts.yml` (with 17 cases in `alerts_test.yml`; a target that stays down for 5 minutes shows as `AlpacaTargetDown`) and its dashboard is `grafana/dashboards/alpaca-trader.json`. The two targets carry the label `service` (`trader`, `observer`): the observer also exports the trader-only gauges (always 0), so the rules and panels for them select `{service="trader"}`. Grafana does not notice a new or changed dashboard file on a Windows bind mount by itself: run `docker compose restart grafana` after editing one.
- Prometheus keeps its time series (15 days, the default) in the named volume `go_prometheus_data`: they survive `docker compose down` and a rebuilt container, and are deleted only by `docker compose down -v` or by removing the volume. Grafana keeps its own database (users, preferences, changes made in the UI) in the named volume `go_grafana_data` the same way; the dashboards stay files in `grafana/`. `GRAFANA_ADMIN_PASSWORD` is read only when that volume is empty; to change the password later run `docker compose exec grafana grafana cli admin reset-admin-password <new>`.

*Security Note: The `user_id` context tracing is critical for tenant isolation and must be securely validated. Furthermore, the `/metrics` endpoint is exposed unauthenticated. The API listens on loopback by default; if you set `LISTEN_ADDR` to a public address, protect it via internal network routing or firewall rules. Because there is no token, the server also refuses (421, logged as a warning) every request whose `Host` header is not `localhost`, `127.0.0.1`, `[::1]`, `host.docker.internal` or the address in `LISTEN_ADDR`: a web page that makes its own domain resolve to `127.0.0.1` (DNS rebinding) still sends its own name as `Host`, so it cannot use the API as if it were the client.*

## How to Run

### Windows (PowerShell, the primary setup)
Prerequisites: Go, Docker Desktop, [Tesseract](https://github.com/UB-Mannheim/tesseract/wiki) with the `bul` and `eng` language data, and [Poppler for Windows](https://github.com/oschwartz10612/poppler-windows) (for example in `C:\poppler-<version>\Library\bin`) — the exact steps are in [Poppler and Tesseract on Windows](#poppler-and-tesseract-on-windows-pdf-text-and-ocr) below; a model server (Lemonade) listening on `LLM_BASE_URL`.

```powershell
# 1. Settings: copy the template and fill it in (GRAFANA_ADMIN_PASSWORD is required)
Copy-Item .env.example .env

# 2. Infrastructure: PostgreSQL (docker-compose.override.yml), embedder, Prometheus, Grafana
docker compose up -d

# 3. Build the backend (main.exe is a build artifact and is not in git) and start it
powershell -ExecutionPolicy Bypass -File scripts\build.ps1
.\main.exe            # or, without building: go run main.go
# main.exe is a snapshot of the code at the time of the build. After every `git pull` or change run
# build.ps1 again, or use `go run main.go`, which always runs the current code.
```

Start the backend **from the repository root**: `migrations`, `prompts` overrides, `storage` and `.env` are relative to the working directory (the start logs their absolute paths). `main.exe` loads `.env` by itself; for a single run you can also set a variable in the shell: `$env:LISTEN_ADDR = "127.0.0.1:8081"`. To pick up a new build, stop the old `main.exe` first (it keeps the file locked). A port that is already taken is reported at start: `netstat -ano | findstr :8080`.

### Poppler and Tesseract on Windows (PDF text and OCR)
Two programs outside Go and Docker read the PDFs and the images: **Poppler** (`pdftotext`, `pdfinfo`, `pdftoppm`) and **Tesseract**. The backend starts them as child processes of the host, so they must be installed on the machine that runs `main.exe`; the Docker containers do not need them. This is how the development machine is set up:

| | Version | Where | Where it comes from |
|---|---|---|---|
| Poppler | 26.09.0 | `C:\poppler-26.09.0\` (the programs are in `Library\bin`) | the zip of a [poppler-windows release](https://github.com/oschwartz10612/poppler-windows/releases), unpacked; there is no installer |
| Tesseract | 5.4.0.20240606 | `C:\Program Files\Tesseract-OCR\` | the Windows installer of the [UB Mannheim build](https://github.com/UB-Mannheim/tesseract/wiki) |
| Language data | `bul`, `eng` (the installer adds `osd` and `script\Cyrillic`) | `C:\Program Files\Tesseract-OCR\tessdata\` | `eng` from the installer, `bul.traineddata` from [tessdata_fast](https://github.com/tesseract-ocr/tessdata_fast) |

**Poppler**
1. Download the release zip (`Release-<version>.zip`) and unpack it so that the `poppler-<version>` folder it contains sits directly under `C:\`. The result must be `C:\poppler-26.09.0\Library\bin\pdftotext.exe`. Keep one Poppler folder only: when several match, the last one by name is used.
2. That is all the backend needs. It looks in `C:\poppler*\Library\bin` (then `C:\poppler*\bin` and `C:\Program Files\poppler*\...`) **before** `PATH`, and logs the programs it picked at startup (`PDF tool … version`). The order matters: Git for Windows ships `pdftotext` from Xpdf, a different program, and it can come first in `PATH`. If Poppler lives elsewhere, set `PDFTOTEXT_PATH`, `PDFTOPPM_PATH` and `PDFINFO_PATH` in `.env`.
3. On the development machine `C:\poppler-26.09.0\Library\bin` is also in the system `PATH`, so the tools can be run by hand; the backend does not depend on it.

**Tesseract**
1. Run the installer (administrator rights) and keep the default folder, `C:\Program Files\Tesseract-OCR`.
2. Bulgarian is not installed by default. Either tick it under "Additional language data" in the installer, or download `bul.traineddata` from [tessdata_fast](https://raw.githubusercontent.com/tesseract-ocr/tessdata_fast/main/bul.traineddata) and copy it to `C:\Program Files\Tesseract-OCR\tessdata\` (administrator rights). The development machine has the `tessdata_fast` file (1 675 212 bytes) next to the installer's own `eng.traineddata`, which is a `tessdata_fast` file too; the larger `tessdata_best` models have not been tried here.
3. Put `C:\Program Files\Tesseract-OCR` into the system `PATH` (on the development machine this was done by hand). The backend runs the bare command `tesseract` and there is no setting for its location. A running process keeps the environment it started with, so open a new terminal and restart `main.exe` afterwards.
4. Check both from a new PowerShell window:

```powershell
tesseract --version        # first line: tesseract v5.4.0.20240606
tesseract --list-langs     # must list bul and eng
& (Get-ChildItem C:\poppler*\Library\bin\pdftotext.exe | Select-Object -Last 1).FullName -v   # pdftotext version 26.09.0
```

**How the backend uses them** (to read a failure):
- A PDF is read with `pdftotext`, its page count comes from `pdfinfo`. Pages with almost no text are treated as scans: `pdftoppm` renders the page at `OCR_DPI` (250 by default) and `tesseract stdin stdout -l bul+eng --psm 3 -c preserve_interword_spaces=1` reads it. An image file goes to the same command directly.
- Tesseract is started single-threaded (`OMP_THREAD_LIMIT=1`), `OCR_CONCURRENCY` pages (6 by default) at a time, and one run is cut off after 2 minutes. These numbers were measured on the development machine (16 threads); see the comments in `internal/ingest/ocr.go`.
- Only Poppler is reported at startup. A missing or broken Tesseract shows up when the first scan or image is ingested: every page fails, the backend gives up after about ten failed pages, and `backend.log` has `tesseract OCR failed`. Run the three commands above to find out which part is missing.
- On Linux the same programs come from the packages `poppler-utils`, `tesseract-ocr`, `tesseract-ocr-bul` and `tesseract-ocr-eng` (not tried with this project).

### Linux / macOS
```bash
docker compose up -d   # the first build downloads the embedding model
export DATABASE_URL="postgres://postgres:postgres@localhost:5432/postgres?sslmode=disable"
export LLM_BASE_URL="http://localhost:13305/v1" # Lemonade LLM URL
export EMBEDDER_URL="http://localhost:8000"

go run main.go
```
`docker compose up -d` starts the whole infrastructure: `db` (from `docker-compose.override.yml`, with a named volume `go_pgdata`), the FastAPI embedder, Prometheus, Grafana and `backup` (the database archive, see below). Their ports are published on `127.0.0.1` only (5432, 8000, 9090, 3000). Every service has `restart: unless-stopped`, so after a reboot (Docker Desktop must start with Windows) they come back by themselves; the backend is not one of them: `main.exe` runs on the host and has to be started by hand. You can use your own PostgreSQL instead if it has `pgvector` and `pg_trgm`.

### Tools & Migrations
Pending database migrations are applied when the backend starts (`AUTO_MIGRATE`, River's own tables as well). To control when that happens — for instance to take a backup first — set `AUTO_MIGRATE=false` and run:
- **Database Migrations**: `go run ./cmd/migrate` (`-status` only lists what is pending), or `goose -dir migrations postgres "$DATABASE_URL" up`
- **River Migrations**: `river db migrate-v5 --database-url "$DATABASE_URL"`
- **Generate SQLC** (after changing `internal/db/queries` or a migration): `sqlc generate`
- **Library maintenance**: `go run ./cmd/reingest -list | -file <id> | -all` (extract and embed the stored originals again; the running backend does the work), `go run ./cmd/reembed [-force]` (see [Embedding model and cache](#embedding-model-and-cache)), `go run ./cmd/recategorize [-apply]` (work out the category of the files again from the stored vectors; it only shows the differences without `-apply`).

### Scripts
Backup, restore and reindex scripts are in `scripts/`; `Backup and Restore.md` has the full guide (in Bulgarian).
- `./scripts/backup.sh` uses `pg_dump -Fc`; `BACKUP_DIR` and `BACKUP_KEEP` (default `backups` / `14` dumps) control where dumps go and how many are kept.
- `scripts\backup.ps1` is the Windows equivalent and falls back to `docker compose exec db pg_dump` when the host has no PostgreSQL client; it also copies `storage\` (the uploaded originals). `scripts\restore.ps1` and `scripts\verify-restore.ps1` restore a dump / prove that a dump restores.
- `./scripts/restore.sh` uses `pg_restore --clean --if-exists`
- `./scripts/reindex.sh` rebuilds concurrent HNSW indices.
- `scripts\backup-task.ps1` registers a daily Windows Scheduled Task (`go-monolith-backup`) that runs `backup.ps1` and keeps the dumps outside the repository.
- The `backup` compose service (`scripts/db-backup-loop.sh`) archives the database while Docker runs, the way the trading bot does: at start and every 6 hours it writes a checked dump without `embedding_cache` (~340 MB in November 2026) and, about once a day, a full one (~600 MB) to `$BACKUP_DIR/auto`, and copies `storage/` to `$BACKUP_DIR/storage`. Failures show as `Backup FAILED` in `docker compose logs backup` and as `unhealthy` in `docker ps`. Settings: `BACKUP_DIR`, `DB_BACKUP_*`, `TZ` in `.env.example`; details in `Backup and Restore.md`.
- `scripts\build.ps1` builds `main.exe`.
- `scripts\cleanup-test-users.ps1` clears the users that live checks leave behind: the API creates a user on the first sight of an `X-User-ID`, so a check against the running backend uses an id from the reserved range `7e570000-0000-4000-8000-<12 hex digits>` ("7e57" reads "test"; e.g. `7e570000-0000-4000-8000-0000000000a1`, never the real user's id and never a random UUID). The script lists that range and what its users own; with `-Apply` it deletes them with everything that cascades, in one transaction. A user that still owns a file that is not deleted stops the run (delete the file with `DELETE /v1/files/{id}` first, or its original stays in `storage\`); a user linked to a Telegram chat is never deleted. The Go tests do not need it: they run on `app_test` and delete their own users.

> **Take backups.** On 2026-10-30 a `DELETE FROM users` cascade wiped the ingested files, the chunks and their embeddings. Nothing could be restored because no dump had ever been taken — the 2026-10-30 incident.

## API
The HTTP API is described in [`docs/openapi.yaml`](docs/openapi.yaml). Every route except `/healthz` and `/metrics` needs the `X-User-ID` header (a UUID; the user is created on first use). The Flet client keeps a copy of the file in its own `docs/openapi.yaml`; change both together.

## Tests

Integration tests **never** read `DATABASE_URL`. They require `TEST_DATABASE_URL`, and they refuse to run unless the database name contains `test`:

```bash
# one-time: create the throwaway database
docker compose exec db psql -U postgres -c "CREATE DATABASE app_test"

export TEST_DATABASE_URL="postgres://postgres:postgres@localhost:5432/app_test?sslmode=disable"
go test -p 1 ./...
```

In PowerShell set the variable with `$env:TEST_DATABASE_URL = "postgres://postgres:postgres@localhost:5432/app_test?sslmode=disable"`.

`-p 1` matters: `internal/db` runs the migrations down to zero and back up, so the packages that share the test database must not run at the same time. Without `TEST_DATABASE_URL` the database-backed tests skip; the pure unit tests still run. Some of them execute `goose.DownTo(..., 0)` and `DELETE FROM users`, which is exactly why they are fenced off from the live connection string. Some tests also need the embedder (`EMBEDDER_URL`). `go test -race` needs a C compiler and does not work on a stock Windows setup; the CI workflow (`.github/workflows/go.yml`) has a separate job that runs it on Linux. A second workflow, `.github/workflows/vulncheck.yml`, runs `govulncheck` (Linux and Windows) on every push to `main` and every Monday, so a new advisory against the Go version in `go.mod` or a dependency the code calls shows up as a red run without any commit.

## Known limitations and considerations
* **Vector Dimensions Validation:** When verifying embedder outputs, avoid hardcoding the dimensions logic like `len(vectors[0]) == 384` across the codebase. The dimension is `config.VectorDimension`; a model with another dimension also needs the `vector(...)` columns migrated and everything re-embedded.
* **Embedder Fallback:** When the embedder fails or returns zero-dimension vectors, the fallback logic should not pad or insert zeroed-out arrays of a fixed size, as this pollutes the database with useless embeddings and degrades hybrid search quality.
* **Web tools:** `web_search` / `web_fetch` can send text from the conversation to external services (the paid search API and the fetched URL). URLs are limited to public `http(s)` addresses, but there is no allowlist of domains.
